AetherCodex 使用说明

版本 2.0.0 · 面向 Codex App 的外部增强启动器与管理工具

这是什么

AetherCodex 由两个程序组成：

程序作用
aethercodex
（静默启动入口）		不显示任何界面。启动 Codex App，注入增强脚本，然后在后台守着连接。日常用它开 Codex。
aethercodex-manager
（管理工具）		控制面板。配置供应商、开关增强功能、管理脚本、查看日志、检查更新。
它不改动 Codex App AetherCodex 不修改 app.asar，不往 Codex 安装目录写任何文件，也不打补丁。Codex 升级后它照常工作；只有当 Codex 的页面结构变化时，才可能需要更新注入脚本。

工作原理

理解这四步，后面所有配置和故障排查都好懂了：

  1. 启动：启动器找到 Codex App 可执行文件，带上 --remote-debugging-port=9229 启动它。这是 Chromium 自带的调试开关，不是破解。
  2. 连接：通过 Chromium DevTools Protocol（CDP）连到这个端口，找到 Codex 的页面目标。
  3. 注入：把增强脚本（renderer-inject.js）注入到页面里。菜单、会话删除、导出、Timeline 这些都来自这个脚本。
  4. 桥接：脚本需要做前端做不了的事（读本地数据库、改配置文件）时，通过本机 helper 端口回调后端。后端还会做心跳检查，掉线自动重注入。

所以：必须用 AetherCodex 入口启动 Codex。直接点原版 Codex 图标不会有任何增强，因为没人给它开调试端口。

安装与入口

Windows

运行 AetherCodex-*-windows-x64-setup.exe。安装到 %LOCALAPPDATA%\Programs\AetherCodex，自动创建桌面和开始菜单快捷方式。

macOS

打开 AetherCodex-*-macos-{x64,arm64}.dmg，把两个 app 拖进「应用程序」。Intel 机器用 x64，Apple Silicon 用 arm64。

macOS 提示「已损坏」 安装包未签名/未公证时 Gatekeeper 会拦截。终端执行： 
sudo xattr -rd com.apple.quarantine "/Applications/AetherCodex.app"
sudo xattr -rd com.apple.quarantine "/Applications/AetherCodex 管理工具.app"

Linux（Ubuntu 24.04 及以上，含 26.04；Debian 13+）

sudo apt install ./AetherCodex-2.0.0-linux-x64.deb

apt 会自动补齐 WebKitGTK 4.1 等依赖，并在应用菜单注册两个入口。其他发行版用 .tar.gz：

tar -xzf AetherCodex-2.0.0-linux-x64.tar.gz
cd AetherCodex-2.0.0-linux-x64
./install.sh            # 装到 ~/.local，可用 PREFIX= 改位置

无桌面会话时可以直接用 aethercodex-manager --install-entrypoints 注册入口。

第一次使用

  1. 打开 AetherCodex 管理工具，停在「概览」页。
  2. 点 检查。健康检查会告诉你 Codex App 有没有找到、入口有没有装好。
  3. 如果提示找不到 Codex App，去「设置」手动填 Codex App 路径（见下方故障排查）。
  4. 需要走自定义 API 就去「供应商配置」，否则跳过。
  5. 回概览点 启动 AetherCodex，或直接用桌面的 AetherCodex 入口。
  6. Codex 起来后，页面里应该能看到 AetherCodex 菜单。没有就看故障排查。

供应商与中转注入

这是 AetherCodex 最复杂也最有用的部分。它通过改写 ~/.codex/config.toml，让 Codex 把请求发到你指定的 API 端点。

三种模式

模式含义适用
官方 Official完全用 ChatGPT 官方登录态，不做任何改写。只用官方订阅。
混合 MixedApi
（默认）		保留官方登录态，同时可以切到自定义 API。切换时不会把 auth.json 弄丢。既有订阅又有中转 Key，想随时切。
纯 API PureApi完全走自定义 API，不依赖 ChatGPT 登录。只有中转 Key，没有官方订阅。

两种协议

  • Responses（默认）—— OpenAI Responses API。原生 Codex 用的就是这个。
  • Chat Completions —— 经典 /v1/chat/completions。大多数第三方中转站支持这个。

选错协议的典型表现是能连通但发消息报错。连接测试失败时，AetherCodex 会自动重试带 /v1 前缀的地址。

配置一个供应商

  1. 「供应商配置」→ 新增。可以用预设选择器一键填好常见中转站的 Base URL、协议和模型列表。
  2. 填 API Key。
  3. 点测试连接。通过后可以拉取模型列表。
  4. 点应用写入 Codex 配置。重启 Codex 生效。
供应商同步 开启后，切换供应商时会同步本地会话的 metadata，切过去之后旧会话仍然看得见，不会「消失」。
中转注入模式下 插件入口解锁和强制安装就不需要了，界面会提示「中转注入模式下无需开启」。会话删除、导出、移动、Timeline 和用户脚本仍然可用。

页面增强

「页面增强」页的每个开关对应注入脚本里的一个能力。总开关关掉则完全不注入。

插件与模型相关

开关作用
插件市场解锁API Key 模式下扩展插件市场请求，尽量显示完整插件列表。官方/混合模式通常不需要。
强制解锁入口强制显示并启用插件入口。API Key 登录时官方会禁用它。
特殊插件强制安装解除 App unavailable 导致的前端安装禁用。
模型白名单解锁从 /v1/models 拉取模型补进列表，让中转站的模型能选。
Fast 按钮显示服务档位切换。Fast 只对 gpt-5.4 / gpt-5.5 生效，其他模型按 Standard 发送。

脚本市场

用户脚本是注入到 Codex 页面的自定义 JS，在增强脚本之后执行。

  • 市场脚本：从远端静态清单加载，可一键安装、更新。
  • 本地脚本：内置脚本和你手动放进去的脚本，可单独启停或删除。

脚本目录见「数据位置」。禁用某个脚本后，需要重载页面或重启 AetherCodex 才能完全移除已执行的效果。

会话管理

直接读 Codex 的本地数据库 ~/.codex/state_5.sqlite。

删除是真删 删除会话会同时删掉数据库记录和对应的 rollout 文件，不是归档。页面内删除支持撤销，管理工具里的删除不支持。

Markdown 导出会把会话导成带时间戳的文件，文件名里的非法字符会自动替换。

Zed 远程项目

当 Codex 会话工作在 SSH 远程目录时，AetherCodex 能识别出远程主机和路径，把文件直接在 Zed Remote Development 里打开。

需要本机装了 Zed，并且 zed CLI 在 PATH 上（macOS 也可以直接识别 /Applications/Zed.app）。「Zed 远程项目」页会显示识别到的项目列表，可以手动清理记录。

更新机制

「关于」页可以检查并启动更新。静默启动器发现新版本时会拉起管理工具并进入更新提示。

更新只会挑选和当前系统、CPU 架构匹配的安装包：

  • Windows → -setup.exe
  • macOS → 对应架构的 .dmg
  • Linux → 优先同架构 .deb，没有则回退同架构 .tar.gz，交给 xdg-open 用系统包管理器安装

故障排查

AetherCodex 菜单没出现

  • 确认是从 AetherCodex 入口启动的，不是原版 Codex。
  • 「页面增强」总开关是否开着。
  • 「关于」页看日志里的 renderer.script_loaded、bridge.request、bridge.response。

找不到 Codex App

各平台的查找位置：

  • Windows：MS Store 包目录，其次 %LOCALAPPDATA%\OpenAI\Codex 等标准安装位置。
  • macOS：/Applications 和 ~/Applications 下的 Codex.app。
  • Linux：/opt、/usr/lib、/usr/share、~/.local/share、~/Applications 下真正含 Codex 可执行文件（Codex/codex/codex-app）的目录，以及名字含 codex 的 .AppImage。

只有确实含可执行文件的目录才会被采纳，所以 PATH 上的 codex CLI 不会被误判成桌面版。自动识别失败时在「设置」里手填路径，Linux 可以直接填 .AppImage 文件路径。

插件里显示后端连不上

先测本机接口：

curl -X POST http://127.0.0.1:57321/backend/status \
  -H "Content-Type: application/json" -d "{}"

接口正常但插件仍超时，通常是页面里的 CDP bridge 或脚本缓存问题。重启 AetherCodex，或在日志里查上面那几个事件。

Linux：管理工具窗口空白

WebKitGTK 渲染问题，先关硬件加速：

WEBKIT_DISABLE_DMABUF_RENDERER=1 aethercodex-manager

Linux：Codex 本体起不来

Ubuntu 24.04 起内核默认开 kernel.apparmor_restrict_unprivileged_userns=1，会挡住依赖 bubblewrap 沙箱的进程创建 user namespace。管理工具自己不用这个沙箱，但被拉起的 Codex（Electron/Chromium）可能中招：

sudo apt install apparmor-profiles
sudo install -m 0644 /usr/share/apparmor/extra-profiles/bwrap-userns-restrict \
  /etc/apparmor.d/bwrap-userns-restrict
sudo apparmor_parser -r /etc/apparmor.d/bwrap-userns-restrict

收集诊断信息

「关于」页有「复制诊断」，会打包版本、路径、入口状态和最近日志，反馈问题时附上它。

卸载

  • Windows：开始菜单的「卸载 AetherCodex」，或设置 → 应用。
  • macOS：把两个 app 拖到废纸篓。
  • Linux：sudo apt remove aethercodex，或 tarball 目录里的 ./uninstall.sh。

「安装维护」页的卸载入口可以选择是否一并删除 ~/.aethercodex 里的设置和日志。Codex 自己的数据（~/.codex）永远不会被删。
